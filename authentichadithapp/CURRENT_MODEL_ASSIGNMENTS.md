## Refresh Rule

This file must be reviewed:

1. Monthly.
2. After any major AI model or tool release.
3. After repeated poor performance from a current model/tool.
4. Before starting a major technical build.
5. Before launching a client-facing service package.
6. Before committing to paid upgrades or new subscriptions.

---

## Replacement Standard

Do not replace a tool unless the replacement improves KP’s actual operating system in one or more areas:

1. Better quality.
2. Faster execution.
3. Lower cost.
4. Better reliability.
5. Better integration.
6. Better context handling.
7. Better business outcome.
8. Better repo-level execution.
9. Better current research capability.
10. Better automation capability.

Do not switch based on hype alone.

## Evaluation Criteria

When reviewing a model or tool, score it from 1-10 in the following categories:

| Category | Meaning |
|---|---|
| Accuracy | How often the output is correct |
| Reasoning | How well it handles complex tasks |
| Coding Ability | How well it handles implementation |
| Repo Awareness | How well it works with real files |
| Tool Use | How well it uses connected tools |
| Context Handling | How well it preserves long context |
| Speed | How fast it produces useful output |
| Cost Efficiency | Whether the value justifies the cost |
| Reliability | Whether it behaves consistently |
| Workflow Fit | Whether it fits KP’s operating system |

---

## Keep / Replace / Test Further / Remove Decision Standard

Use these decisions during every model audit:

### Keep

Use when the current model/tool is still the best fit for the operator role.

### Replace

Use when another model/tool clearly outperforms the current assignment on KP’s actual tasks.

### Test Further

Use when a new model/tool looks promising but has not yet proven itself in KP’s workflow.

### Remove

Use when a model/tool no longer provides enough value, creates confusion, or duplicates another tool’s role.
