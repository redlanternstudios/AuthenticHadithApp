# WORKFLOW_ROUTER.md — Authentic Hadith iOS App

## 1. Purpose

Tells every coding agent and engineer where each problem belongs.

Goal: stop wasting time inside Xcode for issues that live in VS Code, and stop wasting time in VS Code for issues that are truly native iOS.

This file is mandatory startup reading alongside `CLAUDE.md`, `ERROR_REPORT.md`, `BUILD_FIX_LOG.md`, `SYSTEM_RULES.md`, and `APP_LAUNCH_PLAYBOOK.md`.

## 2. Golden Rule

**Default to VS Code. Touch Xcode only when the failure is provably native.**

If the issue can be diagnosed by reading TypeScript, Expo config, Supabase queries, RevenueCat logic, or routing — it is a VS Code problem.

If the issue only surfaces during native compilation, signing, archiving, pods, or Apple submission — it is an Xcode / EAS problem.

When in doubt, classify as `UNKNOWN_NEEDS_TRIAGE` and inspect logs before opening any tool.

Every issue must be classified as exactly one of:

- `VS_CODE_APP_LAYER`
- `EXPO_HYBRID_LAYER`
- `XCODE_NATIVE_LAYER`
- `UNKNOWN_NEEDS_TRIAGE`

Required output before any fix:

```
Classification:
Reason:
Correct tool:
Likely files:
First safe action:
Risk level:
Verification step:

```

Risk level scale:
- **Low** — code edit, no native effects, no commands required
- **Medium** — config change, package install, requires Metro restart or EAS rebuild
- **High** — native regeneration, signing, prebuild, destructive command, App Store submission

## 7. Expo Hybrid Layer

Use this layer when the problem starts in Expo config but affects native iOS output.

### Triggers
- Adding or upgrading a package with native code
- Editing `app.json` plugins, permissions, or bundle identifier
- Editing `app.config.js` extra fields the native side reads
- New iOS permission strings (NSCameraUsageDescription, etc.)
- Bundle ID or build number mismatch between config and EAS build

### Workflow
1. Make the config change in VS Code.
2. Run a fresh Metro start: `npx expo start -c`.
3. If the change touches native code, build via EAS:
   - Preview (TestFlight): `npx eas build --platform ios --profile preview`
   - Production: `npx eas build --platform ios --profile production`
4. Only fall back to local prebuild if EAS cannot resolve the issue.

### Verification
- `npx expo doctor` — SDK compatibility check
- EAS build log — confirms native pipeline accepted the config
- `npx tsc --noEmit` — type sanity
- App boots in TestFlight or simulator

## 8. Xcode Native Layer

Use this layer ONLY when the failure is provably native and unfixable from JS/Expo config.

### Triggers
- Provisioning profile, certificate, or signing identity errors
- Archive or App Store submission failures Apple raises in Xcode Organizer
- Swift or Objective-C compile errors inside `ios/`
- Linker / framework errors during native build
- CocoaPods install or version conflicts
- Entitlement or `Info.plist` issues that Expo plugins cannot resolve
- Native crash logs (.crash, .ips) requiring Xcode symbolication

### Workflow
1. Confirm the issue cannot be fixed from `app.json` / `app.config.js` / Expo plugin first.
2. Open `ios/AuthenticHadithApp.xcworkspace` (NOT `.xcodeproj`) if the folder exists.
3. If `ios/` does not exist, you must run prebuild first — see Section 11 (high-risk).
4. Make the smallest possible change. Do not edit generated Pods code.
5. Mirror the change back into the Expo config layer if possible so it survives the next prebuild.

### Verification
- Local archive succeeds in Xcode, OR
- EAS Build production profile succeeds, OR
- `npx eas submit --platform ios` accepts the build into TestFlight

---

## 9. Do Not Edit — Generated iOS Files

The `ios/` directory is regenerated by `expo prebuild`. Edits inside it are erased on the next prebuild.

### Prohibited unless explicitly authorized
- Editing `ios/Podfile` (use Expo plugins instead)
- Editing `ios/AuthenticHadithApp/Info.plist` (use `app.json.ios.infoPlist`)
- Editing `ios/AuthenticHadithApp.xcodeproj` settings (use Expo config plugins)
- Editing generated Swift / Objective-C bridging files

### Allowed exceptions
- A native bug confirmed unfixable through Expo plugins
- Changes simultaneously mirrored into the Expo config so the prebuild reproduces them
- Approved by KP and logged in `BUILD_FIX_LOG.md` as a native-only fix

If you edit anything inside `ios/`, you MUST log the change and explain why the Expo config layer could not solve it.

│
└─ Cannot tell yet

### High-risk command (KP approval required)

```bash
npx expo prebuild --clean
```

This regenerates `ios/` from scratch and overwrites any local native edits. Run only after:
1. Confirming the issue cannot be solved through Expo config
2. Logging the reason in `ERROR_REPORT.md`
3. Getting explicit KP approval (per `CLAUDE.md` Destructive Commands list)

Other destructive commands also requiring KP approval:
- `rm -rf node_modules package-lock.json`
- `rm -rf ios android`
- Any version upgrade of React, React Native, or Expo

## 11. Verification Rules

A fix is not complete until at least one of the following passes:

| Layer | Verification |
|---|---|
| VS Code App | Feature works in simulator / Expo Go AND `npx tsc --noEmit` passes |
| Expo Hybrid | `npx expo doctor` clean AND EAS preview build succeeds |
| Xcode Native | Local archive OR EAS production build succeeds AND TestFlight accepts upload |

Pre-submission gates (from `APP_LAUNCH_PLAYBOOK.md` Section 5):
- `ERROR_REPORT.md` status is 🟢
- `npx tsc --noEmit` clean
- `npx expo doctor` clean
- `ios.buildNumber` incremented in `app.json` for App Store uploads
- Console statement audit (`SYSTEM_RULES.md` Rule 018)
- Orphan route audit (`SYSTEM_RULES.md` Rule 014)

## 12. Documentation Protocol

After every fix, mandatory updates per `SYSTEM_RULES.md` Rule 012:

1. Add full entry to `BUILD_FIX_LOG.md` (Fix ID, date, root cause, files, exact fix, verification, lesson, pattern category).
2. Reset `ERROR_REPORT.md` status to 🟢.
3. Check the Pattern Tracker. If the bug category has appeared 2+ times, add or strengthen a rule in `SYSTEM_RULES.md`.
4. If deployment or build behavior changed, update `APP_LAUNCH_PLAYBOOK.md`.
5. If new operational guidance was discovered, update `CLAUDE.md`.
6. If a new routing category was discovered, update this file (`WORKFLOW_ROUTER.md`).

No fix is complete until the system has learned from it.

## 13. Escalation Rules

Escalate to KP before acting when:

- Classification is `UNKNOWN_NEEDS_TRIAGE` after reading logs and history
- Fix requires editing inside `ios/`
- Fix requires `npx expo prebuild --clean`
- Fix requires upgrading React, React Native, or Expo SDK
- Fix requires removing or downgrading a production dependency
- Fix touches RevenueCat product IDs, entitlement IDs, or Apple ASC App ID
- Fix touches bundle identifier `com.byred.authentichadith`
- A repeated bug has now appeared 2+ times — propose the new permanent rule instead of patching silently
- App Store submission, TestFlight rejection, or Apple Review reply is involved

When in doubt, ask. The cost of a 30-second confirmation is lower than the cost of a wasted afternoon or a rejected submission.

## 14. Final Operating Rule

VS Code is the daily workspace.

Xcode is only for native iOS build, signing, archive, provisioning, entitlements, pods, linker errors, Swift / Objective-C, native crashes, and App Store archive workflows.

EAS Build is the production iOS pipeline. Local Xcode is the diagnostic tool of last resort.

Classify before acting. Verify before declaring done. Document after every fix.

The system improves with every session. No exceptions.
